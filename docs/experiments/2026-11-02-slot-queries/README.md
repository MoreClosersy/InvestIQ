# S3 试点记录：缺口是“查询不够”还是“结果取少了”？

- 日期：2026-11-02
- 成本：25 次 Tavily `advanced` 搜索（约 50 credits）
- 范围：5 个标的（AAPL / JPM / LCID / NIO / SOFI）× 4 条查询 × 5 结果 + 1 条控制查询 × 20 结果
- 原始数据：[`raw.json`](raw.json)、[`control.json`](control.json)；分析报告：[`report.md`](report.md)
- 未测：LLM 规划。本机 `api.openai.com` 不可达，所以这一轮只测“取数”，不测“由谁决定查询”。

## 结论

1. **主要杠杆是“取多少条”，不是“问几种问题”。**
   严格口径下平均槽位：基线 5 条 **2.00/5** → 同一条查询取 20 条 **4.00/5** → 4 条查询合计约 20 条 **4.40/5**。
   20 条文档时，查询多样性只多 0.4 个槽位，却要多 3 次搜索。
2. **宽松槽位口径不可用。** 它把聚合页导航栏（`SEC Filings`、`Risk Factors`、`IPO Calendar`）当成证据，
   这类页面一多，覆盖率就虚高。严格口径要求关键词出现在标题、或与公司名同句。
   此前 `2026-11-02-coverage` 用的是宽松口径——那组“风险/法律 5/20”应理解为**上界**，真实缺口只会更大。
3. **n=5、单日、单次控制组，不足以证明“查询多样性有价值”。** JPM 是 3 vs 4（4 条查询反而更差），
   NIO 是 5 vs 3。差异方向不一致，规模也在噪声内。

## 这对 ReAct 意味着什么

ReAct 的增益上限被压在“约 0.4 个槽位”这个量级，而代价是 3–4 倍搜索、多轮 LLM 调用、以及一套预算/停止条件。
在拿到更大样本之前，**没有理由先做它**。先把 `max_results` 调大，是同一方向上成本低一个数量级的动作。

## 下一步（按性价比）

1. `max_results` 5 → 20（一行配置），重录 24 ticker 磁带（24 次搜索），跑一次离线评测，量四个数：
   严格槽位覆盖、未接地数字、token/单次成本、p95 延迟。**这是目前唯一有正面证据的方向。**
2. 若扩容后仍缺（试点里 AAPL 缺“重大事件”、JPM 缺“产品/战略”），再加**一条**定向查询，不要上循环。
3. 把严格槽位评分固化进 eval，作为独立指标输出；宽松口径只保留作对照，避免再次误导。

## 局限

- 5 个标的、单日、单次采样；Tavily 排序本身不确定。
- 槽位仍是关键词规则，严格口径也只是降低误判，不等于“证据真的支持结论”。
- 控制组只跑了基线查询的 20 条，没有覆盖“其他查询各取 20 条”。
- 基线 5 条与控制组 20 条是两次独立调用，Tavily 排序有抖动：曲线 n=5 处为 1.80，独立基线为 2.00。
- 20 条里仍混有聚合页（4 条查询去重后聚合页占 38.4%，比冻结语料的 63.3% 低）。
